# How Ariadne compares — a documentation-based capability matrix

> **No product compared here — Ariadne or the commercial ones — was validated experimentally *for this matrix*.** This compares capabilities as described by each vendor's official documentation, as consulted on 2026-10-02. Separately, Ariadne's own collector has been exercised against a real (synthetic, single-node) Kubernetes 1.37.0 lab — see [`compatibility.md`](compatibility.md); the matrix cells below remain documentation-based.

**Status:** MVP complete, offline — documentation-based comparison draft. It does not establish a winner, superiority, performance, savings or price. "Not documented" means *not found in the consulted documentation* — never "not supported".

## Why this matrix exists, and its limits

Ariadne's definition of done includes an honest public comparison with the tools around it. This matrix is built **exclusively from each vendor's official documentation**: manuals, API references, specifications, release notes and official repositories. Every cell carries citation markers (`[P1]`, `[R3]`, …) resolved in the source table at the bottom, which records the consultation date (2026-10-02 for all).

What this matrix does **not** claim:

- It does not claim Kubernetes/OpenShift compatibility for Ariadne beyond the single synthetic Kubernetes 1.37.0 lab exercise reported in [`compatibility.md`](compatibility.md); OpenShift, other releases and managed clouds remain unverified.
- It does not demonstrate native integration between Ariadne and any compared product.
- It does not equate accepting a risk with suppressing an alert, with `not_affected`, or with absence of exploitation.
- It does not equate a hash with authenticity, a signature with truthfulness, or a replay with currency.
- It does not treat a full product, an integration, a CLI and a specification as equivalent.
- It does not validate the runtime-relevance or Red Hat backporting methods of any vendor.
- It does not authorize any release.

Ariadne's own state is reported conservatively: features that exist only as design are labelled **design**, not implemented.

## Reading guide

- **Implemented / design / not done:** Ariadne's documentary state.
- **Per docs:** the vendor's or maintainer's description, without experimental validation.
- **Not documented:** no sufficient support found in the consulted corpus.
- **Partial:** part is documented; the missing part is stated.

Sysdig **Secure** and **Falco** are kept separate: Secure's capabilities are not attributed to Falco. RHACS is anchored to its **4.8** documentation. Prisma cells combine API **34.02** documentation, an official integration and support articles; they are not assumed to describe a single installation. Kubescape and Sysdig publish evolving pages without an unambiguous product version; versions are stated only when the source states them.

## Notes worth keeping

- **Ariadne:** the collector exists as an implemented, accepted read-only component, exercised against one synthetic Kubernetes 1.37.0 single-node lab ([compatibility.md](compatibility.md)); it does not attest a CLI acquisition surface, and M01 rules out only native Prisma import. The exception lifecycle and VEX/SARIF/CSAF export are implemented and reported as such.
- **Prisma:** the expiry behaviour rests on a support article last modified 2022-02-21; a 2026-01-15 article confirms the `Ignore` procedure without revalidating every historical expiry condition. The 2022 article also declares ambiguity when confluent tags carry different actions. SARIF belongs to the consulted integration, not to every API surface. The general Compute documentation page was only retrievable through a search index (`Page Not Found` on direct access) — its deployment statements are therefore the weakest in this matrix.
- **Sysdig/Falco:** `--standalone` prevents describing all of Secure as backend-dependent per operation; the runtime Local Scanning flow does send SBOM/metadata to the backend. The SARIF integration documents limits on the tested scanner versions. Falco is a distinct project: it does not inherit Secure's acceptance workflow, scanner or subscription.
- **RHACS:** anchored to 4.8, not presented as the latest version. Scanner V4 and StackRox Scanner feeds are not interchangeable. Consuming VEX does not demonstrate exporting VEX. Offline mode keeps services, definition maintenance and network configuration.
- **Kubescape:** vulnerability exceptions require `capabilities.riskAcceptance=enable` (documented as disabled by default); OpenVEX generation is experimental and tied to runtime observation. Its documentation links relevance states to package loads observed at runtime; this matrix reproduces the declared method without turning an absent observation into proof of non-affectedness.
- **VEX/CSAF tooling:** representatives are `openvex/vexctl` and `gocsaf/csaf`. Creating, validating, signing or distributing statements does not attest the technical correctness of their claims, nor an approved risk decision.
